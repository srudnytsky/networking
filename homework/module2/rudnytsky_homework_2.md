## Завдання 1. Аналіз відкритих портів

**Команда:**

```bash
ss -tuln
```

Оскільки в системі WSL слухаючих портів небагато, для наочності попередньо було запущено локальний веб-сервер:

```bash
python3 -m http.server 8080 &
```

**Вивід**

```text
srudnytsky@Trinity:~/networking/networking$ ss -tuln
Netid State  Recv-Q Send-Q  Local Address:Port Peer Address:PortProcess
udp   UNCONN 0      0          127.0.0.54:53        0.0.0.0:*
udp   UNCONN 0      0       127.0.0.53%lo:53        0.0.0.0:*
udp   UNCONN 0      0      10.255.255.254:53        0.0.0.0:*
udp   UNCONN 0      0           127.0.0.1:323       0.0.0.0:*
udp   UNCONN 0      0               [::1]:323          [::]:*
tcp   LISTEN 0      4096       127.0.0.54:53        0.0.0.0:*
tcp   LISTEN 0      4096    127.0.0.53%lo:53        0.0.0.0:*
tcp   LISTEN 0      5             0.0.0.0:8080      0.0.0.0:*
tcp   LISTEN 0      1000   10.255.255.254:53        0.0.0.0:*
```

Ключі команди: `-t` — TCP-сокети, `-u` — UDP-сокети, `-l` — ті що очікують з'єднань, `-n` — номери портів без перетворення на назви служб.

Знайдені відкриті порти:

- **TCP порт: 8080** → локальний веб-сервер `python3 -m http.server`. Адреса `0.0.0.0` означає, що сервер слухає на всіх інтерфейсах. Стан: `LISTEN`.
- **TCP порт: 53** → DNS (локальний резолвер `systemd-resolved` на `127.0.0.53` та `127.0.0.54`). DNS використовує TCP для великих відповідей та передачі зон. Стан: `LISTEN`.
- **UDP порт: 53** → DNS. Основні DNS-запити передаються саме через UDP. Адреса `10.255.255.254` — DNS-проксі WSL, через який запити передаються до Windows. Стан: `UNCONN`.
- **UDP порт: 323** → командний порт служби синхронізації часу (chrony, NTP). Слухає лише на `127.0.0.1` та `[::1]`, тобто доступний тільки локально. Стан: `UNCONN`.

Стан `LISTEN` характерний для TCP: сокет очікує на вхідні з'єднання (трикрокове рукостискання). UDP не встановлює з'єднань, тому відкритий UDP-сокет має стан `UNCONN` — він просто приймає датаграми.

## Завдання 2. Аналіз процесів, що слухають порти

**Команда:**

```bash
sudo ss -tulpn
```

Без `sudo` стовпчик `Process` був порожнім, оскільки звичайний користувач не бачить інформацію про процеси інших користувачів (зокрема системних служб).

Результат виконання:

```text
srudnytsky@Trinity:~/networking/networking$ sudo ss -tulpn
Netid State  Recv-Q Send-Q  Local Address:Port Peer Address:PortProcess
udp   UNCONN 0      0          127.0.0.54:53        0.0.0.0:*    users:(("systemd-resolve",pid=148,fd=16))
udp   UNCONN 0      0       127.0.0.53%lo:53        0.0.0.0:*    users:(("systemd-resolve",pid=148,fd=14))
udp   UNCONN 0      0      10.255.255.254:53        0.0.0.0:*
udp   UNCONN 0      0           127.0.0.1:323       0.0.0.0:*
udp   UNCONN 0      0               [::1]:323          [::]:*
tcp   LISTEN 0      4096       127.0.0.54:53        0.0.0.0:*    users:(("systemd-resolve",pid=148,fd=17))
tcp   LISTEN 0      4096    127.0.0.53%lo:53        0.0.0.0:*    users:(("systemd-resolve",pid=148,fd=15))
tcp   LISTEN 0      5             0.0.0.0:8080      0.0.0.0:*    users:(("python3",pid=1984,fd=3))
tcp   LISTEN 0      1000   10.255.255.254:53        0.0.0.0:*
```

Ключ `-p` додає інформацію про процес, який відкрив сокет.

**Процес:** `python3`
**PID:** `1984`
**Порт:** `8080` (TCP)

**Процес:** `systemd-resolve`
**PID:** `148`
**Порт:** `53` (TCP та UDP)

Процес `systemd-resolve` (служба `systemd-resolved`) — локальний DNS-резолвер. Один процес відкрив одразу чотири сокети: TCP і UDP на адресах `127.0.0.53` та `127.0.0.54`. Тому в кожного з них свій дескриптор файлу (`fd=14`, `15`, `16`, `17`), хоча PID однаковий.

Для сокетів на `10.255.255.254:53` та порту `323` процес не відображається навіть із `sudo`. Адресу `10.255.255.254` обслуговує сама підсистема WSL (DNS tunneling), а не процес усередині дистрибутива, тому `ss` не може прив'язати ці сокети до PID.

## Завдання 3. Перевірка TCP-з'єднання

**Команда:**

```bash
nc -vz google.com 80
```

Результат:

```text
srudnytsky@Trinity:~/networking/networking$ nc -vz google.com 80
Connection to google.com (142.251.98.100) 80 port [tcp/http] succeeded!
```

**Тип з'єднання:** TCP
**Порт:** `80` (HTTP)
**Результат:** з'єднання встановлено

`-v` - детальний вивід, `-z` — режим сканування: `nc` лише перевіряє, чи відкритий порт, і не передає дані. Повідомлення `succeeded!` означає, що трикрокове рукостискання TCP (`SYN` → `SYN-ACK` → `ACK`) завершилось успішно, тобто на сервері `142.251.98.100` порт `80` відкритий і приймає з'єднання. Перед з'єднанням `nc` самостійно виконав DNS-резолвінг імені `google.com` в IP-адресу.

## Завдання 4. Порівняння TCP vs UDP

**Команди:**

```bash
nc -vz 8.8.8.8 53
nc -u -vz 8.8.8.8 53
```

Результат:

```text
srudnytsky@Trinity:~/networking/networking$ nc -vz 8.8.8.8 53
Connection to 8.8.8.8 53 port [tcp/domain] succeeded!
srudnytsky@Trinity:~/networking/networking$ nc -u -vz 8.8.8.8 53
Connection to 8.8.8.8 53 port [udp/domain] succeeded!
```

Обидві команди вивели `succeeded!`, але зміст цього повідомлення різний:

- **TCP:** є підтвердження з'єднання. `nc` відправив `SYN`, отримав від `8.8.8.8` відповідь `SYN-ACK` і завершив рукостискання. Отже, `succeeded!` гарантує, що порт `53/tcp` справді відкритий і сервер відповідає.
- **UDP:** немає гарантії відповіді (connection-less). У UDP немає рукостискання, тому `nc` просто відправляє датаграму і не чекає підтвердження. Повідомлення `succeeded!` означає лише, що датаграму вдалося відправити і не надійшло повідомлення ICMP `port unreachable`. Якби порт був закритий або пакет загубився чи був відфільтрований, `nc` міг би все одно показати `succeeded!`.

**Різниця:** TCP встановлює сесію з підтвердженням доставки, тому результат перевірки достовірний. UDP сесію не встановлює тому перевірка UDP-порту через `nc -u` — лише непряма ознака того, що порт відкритий. Для достовірної перевірки DNS через UDP потрібно відправити справжній DNS-запит (наприклад, `dig @8.8.8.8 github.com`) і отримати відповідь.

## Завдання 5. DNS резолвінг

**Команда:**

```bash
nslookup github.com
```

Результат:

```text
srudnytsky@Trinity:~/networking/networking$ nslookup github.com
Server:		10.255.255.254
Address:	10.255.255.254#53

Non-authoritative answer:
Name:	github.com
Address: 140.82.121.4
```

Для перевірки результат продубльовано командою `dig`:

```bash
dig github.com
```

```text
srudnytsky@Trinity:~/networking/networking$ dig github.com

; <<>> DiG 9.18.39-0ubuntu0.24.04.9-Ubuntu <<>> github.com
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 12382
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 1232
;; QUESTION SECTION:
;github.com.			IN	A

;; ANSWER SECTION:
github.com.		45	IN	A	140.82.121.4

;; Query time: 4 msec
;; SERVER: 10.255.255.254#53(10.255.255.254) (UDP)
;; WHEN: Wed Nov 11 19:57:24 UTC 2026
;; MSG SIZE  rcvd: 55
```

**Домен:** `github.com`
**IP:** `140.82.121.4`
**DNS сервер:** `10.255.255.254` (порт `53`)

DNS-сервер `10.255.255.254` вказаний у файлі `/etc/resolv.conf` (`nameserver 10.255.255.254`). Це внутрішній DNS-проксі WSL, який передає запити DNS-резолверу Windows. Ця ж адреса була в завданнях 1 і 2 як сокет на порту `53`.

Позначка `Non-authoritative answer` означає, що відповідь надав не авторитетний сервер домену `github.com`, а проміжний резолвер (можливо, із кешу). У виводі `dig` видно додаткові деталі: запис типу `A` (IPv4-адреса), `TTL = 45` секунд (час, протягом якого відповідь можна кешувати), статус `NOERROR` та те, що запит передано через UDP.

## Висновок

Під час роботи було досліджено транспортний рівень і мережеві служби Linux у середовищі WSL. За допомогою `ss -tuln` визначено відкриті TCP- та UDP-порти та їхні стани (`LISTEN` для TCP і `UNCONN` для UDP), а `sudo ss -tulpn` дав змогу визначити процеси, що відкрили ці порти, та їхні PID.

За допомогою `nc` перевірено встановлення TCP-з'єднання з `google.com:80` і порівняно поведінку TCP та UDP на прикладі DNS-сервера `8.8.8.8`. Встановлено, що успішна перевірка TCP-порту підтверджується рукостисканням, тоді як для UDP аналогічний результат не гарантує, що сервер справді отримав дані.

Також виконано DNS-резолвінг домену `github.com` командами `nslookup` і `dig`: отримано IP-адресу `140.82.121.4` і визначено, що відповідь надав DNS-проксі WSL `10.255.255.254`.
